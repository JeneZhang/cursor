# Cursor Cloud Computer 升级方案

依据全部来自 [`current-state.md`](./current-state.md) 的实测数据。每一项都写清
**现象 → 根因 → 改法 → 预期收益 → 怎么验证 → 风险**，收益全部用实测数字算出来，
验证全部落到 [`tools/cloud-desktop-audit`](../../tools/cloud-desktop-audit/) 的某个 section。

## 目标与约束

优先级排序按"agent 完成一个 GUI 任务的正确率和耗时"来定，而不是按"桌面看起来好不好"。

约束：

- 4 vCPU、无 GPU、纯软件渲染。任何方案的 CPU 预算都要和被测应用共享。
- 帧缓冲分辨率和模型可见分辨率强耦合（`CoordinateScaler` 只容许 2% 宽高比偏差），
  改一边必须同时改另一边。
- 分成两类改动：**只动 exec-daemon**（可以立刻发、立刻量）和**要重建镜像并重新烤快照**
  （周期长、回滚贵）。方案按这个界线分批。

## 收益概览

一次"点击 + 截图"的往返，今天是 `103 ms 动作 + 2000 ms 固定等待 + 142 ms 截图 ≈ 2245 ms`。
做完 P0/P1 之后约 `103 + 426（含截图） ≈ 529 ms`，**约 4.2 倍**。
一个 40 步的 GUI 任务，纯等待时间从约 90 秒降到约 21 秒。

| 项 | 现状 | 改后 | 类型 |
| --- | --- | --- | --- |
| 重复坐标的鼠标动作 | 15 192 ms | 1.6 ms | 只动 daemon |
| 中文 `type` 完全正确率 | 9/18 | 18/18 | 只动 daemon |
| 敏感场景人工介入 | 无任何机制 | 策略 + `needs_human` 事件 + noVNC 深链 | daemon + 平台 |
| 截图前等待 | 固定 2000 ms | 典型 426 ms（上限仍 2000 ms） | 只动 daemon |
| 模型可见画面 SSIM | 0.876 | 0.931 | 只动 daemon（一个常量） |
| 录屏采集 CPU | 1.18~1.63 核 | 0.59~0.80 核 | 只动 daemon |
| 录屏 staging 体积 | 385~555 MiB/min | 178~247 MiB/min | 只动 daemon |
| CJK 可选字族数 | 2（韩文 1） | Noto Sans CJK 全字重 | 需重建镜像 |

## P0-1 去掉 `mousemove --sync`

**现象。** 指针已经在目标坐标上时，`xdotool mousemove --sync X Y` 阻塞 **15 192 ms**；
带点击的动作串阻塞 **15 289 ms**。正常路径只要 1.6 ms / 103 ms（§4.1）。

**根因。** `--sync` 的语义是"等指针**离开**原来的位置"。目标等于当前位置时这个事件永远
不会发生，xdotool 一直重试到自己放弃。executor 对每个带坐标的动作都发
`mousemove --sync`，且没有做去重，所以"对同一个坐标连续操作"必然踩中：重复点同一个按钮、
截图确认后再点一次、双击被拆成两个 `click`、拖拽首个路径点正好在指针下。

**改法。** 首选**直接去掉 `--sync`**。XTEST 的指针移动由服务器同步应用，请求发出去之后
指针就在目标位置了；`--sync` 并不能保证*应用*已经处理完这次移动，所以它换来的只是一个
不可靠的延迟和一个 15 秒的地雷。同一次 `xdotool` 调用里的子命令本身就是有序的，
移动和点击的先后关系不受影响。

保守替代方案：保留 `--sync`，但先用 `getmouselocation`（1.9 ms）比对，坐标相同就跳过移动。
多一次进程启动（1.4 ms），换掉 15 秒。

无论选哪个，都应该同时**把 `xdotool` 的超时从 30 秒收到几秒**并明确报错。现在
`DEFAULT_TIMEOUT_MS = 30000`，正是它让 15.2 秒的阻塞悄无声息地通过。

**验证。** `audit.py input`：`已在目标位置` 那两行必须掉到和 `需要移动` 同一量级。

**风险。** 有些应用依赖 hover 状态在按下之前更新；去掉 `--sync` 后这个间隔消失。
这类需求应该由 P1-1 的自适应沉降统一处理，而不是靠一个副作用式的延迟。

## P0-2 修好非 ASCII 打字

**现象。** 默认路径在中文用例上 18 次只有 9 次完全正确，会静默丢字；`xdotool` 仍返回 0。
真实 `computer_use` 调用里打 `延迟` 只到了 `延`（§4.5）。

**根因。** 默认路径逐字符借还 keycode，应用按自己缓存的键盘映射解释按键，抢在服务器
`MappingNotify` 之前到达的按键按旧映射解析后消失。代码注释已经记录了这个问题
（`Aprenderás` → `Aprenders`），并给出了 `bindUnmappedCharacters` 这条正确路径，
但它**默认关闭**。

**改法。** 分三步：

1. **把 `bindUnmappedCharacters` 默认打开。** 立刻拿到正确性：实测全部用例全对。
   代价是中文吞吐从 136 ch/s 掉到 17 ch/s。
2. **加剪贴板快路径。** 镜像里已经有 `xclip`。对含非 ASCII 的整段：先存下原剪贴板
   （`xclip -o`），`xclip -selection clipboard -i` 写入，发一次 `ctrl+v`，再恢复原剪贴板。
   一次 X 往返、不改键盘映射、结果按构造就是精确的，预计 20~50 ms——比两条现有路径都快。
   注意它改变了语义：终端要 `ctrl+shift+v`，部分应用会拦截粘贴，剪贴板本身是共享资源。
   所以做成可选，并按"借用 keycode 需要拆几轮"来决定默认走哪条：一轮能打完就用 keycode
   路径（语义最干净），需要多轮就用剪贴板。
3. **扩大空闲 keycode 预算。** 现在只有 **19 个**空闲 keycode，一段中文里不同字超过 19 个
   就必须拆轮，每多一轮多 600 ms 的映射沉降。X 的 keycode 上限是 255，会话启动时预留一个
   更大的连续区段（比如 40 个），多数中文句子就能一轮打完。

**验证。** `audit.py typing`：所有行 `exact` 必须是 `6/6`，且中文吞吐回到接近 ASCII 的量级。

**风险。** 剪贴板路径会动用户/应用的剪贴板——必须保证恢复，且在恢复失败时报错而不是静默。
keycode 预留要和别的会话级 keycode 使用者协调（现在没有，但要写进注释）。

## P1-1 把固定 2000 ms 等待换成自适应沉降

**现象。** 截图前固定睡 2000 ms。实测画面稳定只需要 239~398 ms（还是含约 96 ms 探测滞后
的上界，真实值 100~250 ms），一次截图本身 142 ms。一次往返里约 93% 是干等（§4.2、§4.3）。

**改法（无新依赖、可立刻发）。** 把"睡 2 秒然后截一张"改成"**边截边比**"：

```
frame = capture()                       # 142 ms，就是正常的截图链路
loop until 2000 ms 上限:
    next = capture()
    if next == frame: return next       # 画面已静，手上这张就是要交的截图
    frame = next
```

典型情况 3 次抓取 ≈ **426 ms**，而且最后那张直接当截图交出去，不用额外再截一次。
上限仍是 2000 ms，所以最坏情况和今天完全一样——**没有回归面**。持续动画（转圈、视频）
永远比不稳定，自然落回上限，也就是今天的行为。

**下一步（要写原生代码）。** 这台服务器有 `DAMAGE` 扩展。把每次截图都新起一个 `ffmpeg`
换成一个常驻采集组件：用 `MIT-SHM` 直接读帧缓冲、进程内用 libwebp 编码、同时订阅
`DAMAGE` 事件。这样一次抓取从 142 ms 降到几毫秒，沉降判定从"轮询比图"变成"等 damage 静默
80 ms"，两个问题一并解决。exec-daemon 已经在分发原生模块
（`polished-renderer.node`、`pty.node`），加一个不破坏现有形态。

顺带说明 §4.3 里两个**不要做**的"优化"：截图不要换有损 WebP（实测 96 KiB vs 无损 36 KiB，
界面内容有损反而更大也更糊），也不要换 PNG（大 20 倍）。缩放算法换 lanczos/area
差异肉眼可忽略，单独换不值得。

**验证。** `audit.py settle` 给出真实沉降时间；`audit.py screenshot` 给出单次抓取成本。
两者相加就是新的往返时间。

**风险。** "两帧相同即视为静止"会漏掉恰好在两次抓取之间完成又回弹的变化。要求连续 N 帧
（现在的探针用 3 帧）相同可以缓解，代价是多一次抓取。

## P1-2 换掉 1.5 倍这个缩放比

**现象。** 模型可见 1280x800，SSIM 0.876。1.5x 几乎没比 2.0x（0.859）好，而 1.25x 是
0.931（§4.4）。非整数缩放比额外损失细节，1.5x 正好落在最不划算的位置。

**改法。** 两条路，建议先走第一条：

**(a) `API_WIDTH` 1280 → 1536。** 一个常量。宽高比不变（1536/960 = 1.6），
`CoordinateScaler` 的检查照样通过。SSIM +0.055，图像像素 +44%（1.02 → 1.47 MP）。

**(b) 帧缓冲改成模型可见分辨率的整数倍。** 保持 `API_WIDTH = 1280`，帧缓冲改
**2560x1600 且桌面 2 倍缩放**（`GDK_SCALE=2`、`QT_SCALE_FACTOR=2`、Chrome/Electron 加
`--force-device-scale-factor=2`）。模型看到的就是一个逻辑 1280x800 的桌面，
以真正的 1:1 逻辑像素呈现，缩放是精确的 2:1 整数盒式滤波——清晰度上限最高。

关于 (b) 必须说清楚的历史：镜像里那份 `anyos.hidpi.conf` 说明 HiDPI 路线**走过又退回来了**，
当时用的是 3840x2400（像素量是今天的 4 倍）。2560x1600 只有 **1.78 倍**，不到当年的一半，
这是重提这条路的唯一理由。代价也要说清楚：逻辑桌面从 1920x1200 缩到 1280x800，
能同时摆开的窗口变少。

**验证。** `audit.py fidelity` 给 SSIM 与像素量。但 SSIM 只是代理指标——真正该看的是
任务成功率，所以 (a) 上线时要把图像 token 增加 44% 的成本和成功率变化一起衡量，
不能只看 SSIM 涨了。

**风险。** (a) 直接增加每张截图的 token 成本和上下文占用。(b) 是耦合改动：`anyos.conf`
的物理尺寸项（光标、dock 图标、面板）、Chrome/Electron 的 scale factor、录屏代理里
硬编码的 `scale=1920:-2`、以及 `CoordinateScaler` 的宽高比检查必须一起改。

## P1-3 敏感场景的人工介入通道

**现象。** 支付、验证码、2FA、需要填密钥的界面，这条链路上**没有任何检测或移交机制**
（`captcha` / `payment` / `askUser` / `requestHumanInput` 在 14.1 MB 的 daemon 里命中数
全为 0，详见 [`product-overview.md` §2.6](./product-overview.md)）。agent 会继续操作下去，
而屏幕上出现过的东西会进入留存的截图（实测一次会话积累 55 个 `.webp`），
录屏时还会进入**会被上传到用户 Dashboard** 的产物。

**不要做的事：靠模型识别"这是不是支付页"。** 这类判断不可靠，漏检的后果又不对称
（漏一次可能就是一笔真实支付）。检测应该只作为提示，不能作为闸门。

**改法，分三块。**

**(a) 声明式策略，而不是内容检测。** 任务开始时由调用方声明边界——允许的域名、
禁止的操作类别——越界就停。这和现有的 egress 白名单是同一套思路，是确定性的。
可用的结构化信号（按可靠性排序）：

| 信号 | 来源 | 覆盖范围 |
| --- | --- | --- |
| 当前 URL / 域名 | Chrome CDP（9222 端口已经开着） | 仅浏览器 |
| `input[type=password]`、`autocomplete="one-time-code"`、reCAPTCHA iframe | CDP 查 DOM | 仅浏览器 |
| 窗口标题（`_NET_WM_NAME`） | X 属性 | 所有窗口，但信息量低 |

必须说清楚**覆盖是不完整的**：桌面应用没有 DOM 这种可观测性，只能拿到窗口标题。
所以策略层要能表达"未知应用里禁止某类操作"，而不是假装能看懂所有界面。

**(b) 一个真正的"暂停并请求人工"原语。** 现在 agent 只能结束回合并在回复里说明，
而这在 UI 上和"我做完了"没有区别。需要的是：

1. 一个能把 `needs_human` 事件写进 Dashboard 事件流的原语（复用现有事件机制，
   `logLevel: warn`，现在只有 `pr_created` / `artifact_created` / `mcp_auth_error` 这些 kind）。
2. 事件里带 **noVNC 的深链**，让用户一键进到那个桌面，而不是自己去找端口。
3. 会话保持"我在等你"的状态，而不是看起来已经结束。
4. **切换输入所有权**，见下。

**(b2) 输入所有权：闸门已经在机器上了，只是没接线。** 人和 agent 的输入之间目前
毫无仲裁：一个会话只有一个指针和一个键盘焦点，后写的覆盖前一个，人在 agent 打字中途点
一下别的窗口就能把后续按键截走（实测 62 个字符里 44 个投递到了别的应用，
详见 [`product-overview.md` §2.5](./product-overview.md)）。

而 TigerVNC 支持按输入类别关闭 RFB 通道，并且**可以在运行时用 `vncconfig` 改**，
实测能挡住人的输入而完全不影响 agent 的 XTEST 输入：

```
vncconfig -set AcceptPointerEvents=0   ->  人被挡住，agent 照常工作
vncconfig -set AcceptPointerEvents=1   ->  人恢复
```

当前 `AcceptPointerEvents` / `AcceptKeyEvents` / `AcceptCutText` / `SendCutText`
全是默认值 1，启动参数里一个都没设。所以可以直接做成两种明确的模式：

| 模式 | 闸门 | 用在什么时候 |
| --- | --- | --- |
| agent 独占 | `AcceptPointerEvents=0`、`AcceptKeyEvents=0` | agent 正在执行动作序列，人只能看 |
| 人接管 | 两者都 `=1`，同时 agent 暂停发动作 | 命中敏感策略、或用户主动要求接管 |

关键在于**任何时刻只有一方持有输入权**，切换是显式的、有事件记录的。这样 §2.5 里那三个
现象（拖拽落点被改、打字被截走、指针来源不可辨）就都不会发生。
noVNC 客户端侧的 `view_only` 参数不能用来做这件事——那只是前端不发事件，
换个客户端就绕过了；闸门必须在服务器侧。

需要配套的一点：闸门关着的时候，人在 noVNC 里的操作会**静默失效**，这很容易被误认为
卡住了。所以 UI 上必须显示当前是谁持有输入权。

**(c) 敏感期间停止留存。** 把 secret 遮蔽扩展到像素是做不到的（通用的屏幕内容打码不现实），
但可以做两件确定的事：处于策略标记的敏感状态时，**暂停截图落盘与产物上传**；
浏览器里已知的密码类输入框，截图前用 CDP 拿到元素边界框做遮挡——同样只在浏览器里可行。

**验证。** 这一项无法用 `audit.py` 验证，它需要的是端到端的策略测试：
构造一个带 `input[type=password]` 和 reCAPTCHA iframe 的页面，确认 agent 停下、
事件流出现 `needs_human`、且该状态下没有新截图落盘。

**风险。** 策略过严会让 agent 频繁停在正常流程上（比如任何登录页都停），
反而降低自主性；所以策略必须由调用方按任务声明，而不是全局默认开到最严。
另外 (c) 会让"出问题时的现场证据"变少——这是有意的取舍，需要在文档里写明。

## P2-1 降低录屏采集成本

**现象。** 60 fps 全 I 帧 crf 17 占 1.18~1.63 核（共 4 核），staging 写 385~555 MiB/min。
而 34 秒会话的成片只有 4.08 MB（§4.6）。

**改法。** 采集与输出降到 30 fps、`crf 17 → 20`，保留全 I 帧（后处理要任意跳帧）。
实测 CPU 降到 0.59~0.80 核（**约 −50%**），staging 降到 178~247 MiB/min（**约 −55%**）。
成片本来就受 `PROXY_TARGET_FPS` 限制且会重新编码，30 fps 对"演示 GUI 操作"完全够用。

**为什么不只是省磁盘。** 在 4 vCPU 上编码器要和被测应用抢 CPU，于是**录着屏跑的 GUI 测试
和不录屏跑的时序不一样**——录屏这个动作本身影响了它记录的对象。砍掉一半 CPU 是在减少
这个观测偏差。

**验证。** `audit.py capture` 三个变体的对照就是决策依据。

**风险。** 快速动画在 30 fps 下更容易看出跳帧。如果某些演示确实需要 60 fps，
做成按录制请求可选，而不是全局降级。

## P2-2 补齐字体，修好回退顺序

**现象。** 没装 Noto Sans CJK；中日韩只有 2 个可选字族（韩文 1 个），且都不含在 UI 字体
Inter 里；emoji 会先落到 DejaVu Sans 而不是已装的 Noto Color Emoji；阿拉伯文/希伯来文
落到 DejaVu Sans 而不是已装的 Noto Sans Arabic/Hebrew（§4.7）。

**改法。**

1. `vnc-desktop.Aptfile` 加 `fonts-noto-cjk`（需要全字重再加 `fonts-noto-cjk-extra`）。
2. 加一份 fontconfig 规则（例如 `/etc/fonts/conf.d/60-anyos-fallback.conf`）：
   给 Inter / JetBrains Mono 追加 Noto Sans CJK SC/TC/JP/KR 作为回退；
   emoji 码位把 Noto Color Emoji 排到 DejaVu Sans 之前；
   阿拉伯文/希伯来文把对应的 Noto Sans 排到 DejaVu Sans 之前。

**为什么值得。** 模型是通过一张再缩小 1.5 倍的截图去读这些字的。单字重（粗体只能靠合成）、
老式 hinting 的兜底字体，正是这条链路上最差的输入。这一项和 P1-2 是互补的：
一个提升"传输保真度"，一个提升"信源质量"。

**验证。** `audit.py fonts`：CJK 覆盖字族数应显著大于 2 且解析到 Noto Sans CJK；
emoji 应解析到 Noto Color Emoji。

**风险。** `fonts-noto-cjk` 会明显增大镜像。如果镜像体积敏感，可以只装 SC + JP + KR
的常用字重，而不是 `-extra` 全量。

## P2-3 加上按动作粒度的观测

**现象。** 现有指标是会话级的：`computer_use.session.duration_ms`、`action_count`、
`action_kind`。一个 15.2 秒的单动作阻塞被摊进整段会话时长里，看不出来。
P0-1 这个量级的问题能长期存在，本身就是观测粒度不足的证据。

**改法。** 补三类指标：按动作类型的耗时直方图；实际沉降等待时长与上限的比值
（这个直接量化 P1-1 的收益）；打字路径的分布（naive / keycode / 剪贴板）与拆轮次数。
再加一条超时告警：任何单个 `xdotool` 调用超过阈值就记一条明确的错误，而不是静静等完。

**验证。** 不由审计脚本验证——这一项的意义就是让下一个同类问题不必靠审计脚本才发现。

## P3 组件版本

`noVNC 1.2.0`（2020）和 `websockify 0.10.0`（2021）是人看画面的那条路；
`xdotool 3.20160805.1`（2016 年构建）是 agent 操作的那条路。

`xdotool` 尤其值得处理：P0-1 的坑就来自它的 `--sync` 语义。在调用方绕开仍然是对的，
但换成直接调 XTEST 的绑定（不再每个动作起一个进程）可以同时省掉每次 1.5 ms 的进程启动
并彻底移除这个语义陷阱。这件事和 P1-1 的常驻采集组件是同一个方向：
**把 X 交互从"每次 fork 一个 CLI"变成"一个常驻的 X 客户端"**。

## 分批落地

**批次 A — 只动 exec-daemon，不重建镜像。** P0-1（去 `--sync` + 收超时）、
P0-2 第 1 步（`bindUnmappedCharacters` 默认开）、P1-1 第一段（边截边比）、
P1-2 (a)（`API_WIDTH` 常量）、P2-1（30 fps / crf 20）、P2-3（指标）。
全部可以用 `audit.py` 逐项验证，出问题回滚成本低。

**批次 B — 仍只动 daemon，但要写新代码。** P0-2 第 2、3 步（剪贴板路径、keycode 预留）、
P1-1 第二段（`MIT-SHM` + `DAMAGE` 常驻采集组件）、P3（XTEST 绑定替掉 `xdotool` 进程）。
P1-3 也落在这里，但它还需要平台侧配合（事件流新增 kind、Dashboard 上的等待状态），
不是纯 daemon 改动。

**批次 C — 重建镜像并重新烤快照。** P2-2（Noto CJK + fontconfig）、
P1-2 (b)（2560x1600 + 2 倍缩放，只在 (a) 之后仍然是瓶颈时才做）、P3 剩下的版本升级。

## 验证矩阵

| 改动 | 用哪个 section 验证 | 通过标准 |
| --- | --- | --- |
| P0-1 | `input` | `已在目标位置` 与 `需要移动` 同量级 |
| P0-2 | `typing` | 所有行 `exact = 6/6`，CJK 吞吐接近 ASCII |

## 明确不做

- **截图换有损编码或 PNG。** 实测有损 WebP 比无损更大（96 vs 36 KiB）且更糊；PNG 大 20 倍。
- **只换缩放算法。** lanczos +4 ms/+3 KiB、area −7 ms/−2 KiB，肉眼差异可忽略。真正的杠杆是
  缩放比，不是滤波器。
- **关屏幕保护。** 看着像隐患，实测不是：把超时压到 5 秒空转 12 秒，帧缓冲亮度毫无变化，
  Xtigervnc 不做 blanking，且没有 DPMS 扩展。
- **回到 3840x2400 的 HiDPI 配置。** 像素量是今天的 4 倍，而且这条路已经走过又退回来了。
  如果要动分辨率，2560x1600（1.78 倍）才是值得讨论的点。

## 遗留观察（不构成改造项）

- 录屏用 `-draw_mouse 0`，成片里的光标完全由事件日志重建。因此不经过 computer-use 的
  指针移动（应用自己挪的、人在 noVNC 上操作的）在成片里没有光标。如果以后要支持
  "录人工操作"的场景，这里需要另一套处理。
- VNC 是 `-SecurityTypes None` + `-localhost`，只监听回环，对外只有 websockify 端口。
  只要那个端口不外泄就没问题，但这意味着**端口暴露是唯一的边界**。
